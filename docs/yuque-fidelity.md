# 第 二十五节 · 导入：原地弹框 + 落在当前库（2026-10-18）

用户报：**「点击导入后跳转到另外的界面」**。

## 事实：之前确实在换页面

侧栏 `＋ → 导入…` 的实现是 `navigate('/settings?tab=data&import=1')`：
把用户扔去设置页、落到「数据管理」页签、再自动打开格式选择器。

那是**回避而不是解决**。用户站在某个库的目录里要点「导入」，
落地时已经不知道自己刚才在哪个库了 —— 而导入结果恰恰是要放进那个库的。

## 依据：语雀的导入永远针对一个知识库

两条**互相独立**的来源，指向同一件事：

| 来源 | 原文要点 |
|---|---|
| 语雀官方 Lake 文档（yuque.com/go/doc/171735435） | 步骤 2 就是「**选择知识库的导入**」 |
| 简书教程（2020，含逐步截图） | 第 6 步「如果需要继续导入文档，返回上一步，在**左侧目录小＋号**里继续导入」 |

而工作台级的入口是另一回事：第三方问答里记录的是
「工作台 → 新建 → 导入 → **选择需要导入到的知识库**」。
也就是说：**语雀从不静默新建一个库**，它要么用你已经在看的那个，
要么问你要哪一个。

## 改了三件事

### ① 入口不再换页面

整套导入从 `Settings.tsx`（2195 行 → 1295 行）搬成
`src/components/doc/ImportDialog.tsx`（977 行），
目录树与设置页渲染的是**同一份**。

搬而不是抄：那五个弹窗依赖一整套状态（预览计划、原始字节、进度、落库守卫），
抄一份就是「同一份逻辑两处、必漏一处」。
抽取用脚本按**内容锚点**切片 + 边界断言，不靠手抄 600 行。

### ② 导入落到当前库

`ImportDialog` 接一个 `targetBookId`：

- 有（目录树进来）→ 直接导进**当前这个库**，只需要该库的写权限
- 没有（设置页进来，用户不在任何目录树里）→ 退回新建一个，
  并由选择器把这句话**写在界面上**

⚠️ 之前是**无条件新建**（`spaces[0]`）。那不只是别扭：
新建库要**空间管理员**，而普通成员恰恰是有目标库写权限的 ——
于是他在自己正在编辑的库里点导入，一路走完到落库那一刻才被拒。

### ③ 落点写在界面上

选择器顶上那行「导入到哪里：…」，
两种落点都写出来。**不写出来，用户就只能靠导完之后翻遍知识库列表才知道东西去哪了。**

## 顺手挖出来的三个真缺陷

### 1. 判据把**错误行为**钉成了硬要求

`test-import-ui.mjs` 原来有一条：

```js
ok(/settings\?tab=data&import=1/.test(treeCode),
  '导入跳去设置页的唯一那份实现，不在树上复制一套弹窗')
```

也就是说「点导入必须跳设置页」被写成了判据，而且它一直绿。
**判据固化了一个错误行为，比没有判据更难拆** ——
后来的人看到它绿，会以为那是刻意的设计。

现在改成钉正确行为，并加了一节「只有一份实现」：
扫全项目，断言 `ImportPicker` / `ImportProgress` / `ImportDialog`
**各只声明一次**、`createBook` 在导入路径里**只出现一次**。
判据不钉「住在哪个文件」，只钉「有几份」——
这样以后再搬家也不用改判据，而真抄了第二份立刻会红。

### 2. `books` 是数组，我当字典查了 → 界面显示**假书名**

```tsx
books[targetBookId]?.name || '未命名'   // ❌
```

`books` 是 `Book[]`。用字符串下标取**取不到任何东西**，
于是落进硬编码兜底 —— 真机实测：这本书明明叫「导入的 Word 文档」，
提示却写「导入到当前知识库『**未命名**』」。

**一个写死的兜底比没有兜底更坏**：没有的时候至少知道自己没查到。
现在查不到就明说「它的名字读不到了 —— 这一本可能刚被删除」。

> 这一族我栽过：`data[实体名]` 是数组不是字典。
> 判据是「同一次调用里出现两个 id 空间要逐个确认」，
> 这里换成「先确认容器是数组还是字典，再决定用不用下标」。

### 3. 「关掉之后就再也开不了」——真机实测才发现

格式选择器关闭时只 `setPickOpen(false)`，**从不通知调用方**。
于是调用方的 `open` 停在 `true`、组件里的 `wasOpen.current` 也停在 `true`：

```
用户第二次点「导入…」 → setOpen(true) 是**空操作**
                      → open 没变 → effect 不跑 → 弹窗再也不开
```

症状是「第一次能开、之后永远没反应」，而**控制台一句错都没有**。
纯静态看不出来 —— 是真机点开、关掉、再点才发现第二次没反应。

现在关选择器时同时 `setPickOpen(false); onClose()`。
新增套件 `test-import-inline.mjs` 把「关掉再开」钉成断言，
另外两条钉「落点提示 == 侧栏那本书的真名」「导入后 `doc.bookId` 就是当前 bookId、
且知识库数量没变」。

## 一条判据上的自我修正

中途我一度以为「`.yq-imppick` 的样式在 `Help.css` 里、
而只有 `Help.tsx` 引用了它，所以设置页和目录树里那个框是没样式的」。

**那个判据是错的**：`App.tsx` 里 `import Help from '@/pages/Help'` 是**急切导入**（不是 lazy），
所以 `Help.css` 进首屏 bundle，规则全局生效。
关键不在「谁 import 了它」，而在「它有没有进首屏 chunk」——
和「配置项里列的东西 ≠ 产品真的渲染了」是同一族。

（另外那次误判还顺手暴露了一件事：DOM 里出现过
`class="yq-tree-cat-add" title="新建文档"`，而源码里那个类名是
`title="新建 / 导入"` —— 说明**浏览器标签页还跑着旧 bundle**。
「服务端在发新文件」和「页面已经加载新代码」是两件事。）

## 回归

`test-import-ui.mjs` 35 → **54** 项（新增 19 项），
外加新套件 `test-import-inline.mjs`（真浏览器，走完整条交互）。
判据全部做过**破坏对照**：把「又跳设置页」「不传 bookId」
「resolveTarget 不优先用目标库」「第二处 createBook」
「books 当字典查」逐条破坏，五条都真的变红，还原后回绿。

## 补记 · 同一晚的三件收尾（2026-10-18 16:50）

### ① 两条**过期**的套件，都是上一轮改界面时漏掉的

上一轮把侧栏 `＋` 从「点一下直接建文稿」改成了「开一个菜单」（照实测语雀），
但两条套件还断言着**旧形态**，而那一轮全量回归被中止了 —— 于是它们**从没被人看见**。

| 套件 | 断的是什么 | 真相 |
|---|---|---|
| `test-catalog-row-e2e` | 「点 ＋ 建出了一篇文稿」 | ＋ 现在开菜单；要断的仍然是「＋ 真能用」，所以改成点菜单里的「文档」 |
| `test-create-denied` ⑩ | 「底部工具栏的 ＋ 和 ⋯ 对读者不出现」 | 底部工具栏连同它的 ＋ **早就搬走了**，只有一条 CSS 还留着 |

顺带挖出一条**死 CSS**：`.yq-tree-add-more` 在组件里已经搜不到，
只有 `Tree.css` 里还有两条规则 —— 而 `test-create-denied` 正是照着它写的断言。
删掉它的理由不是「不好看」，是**它让后来的人以为那个按钮还在**。

> 「套件红」有两种：一是我刚改坏的，二是它**早就在红**而没人跑。
> 后者更阴 —— 它让红色的总数看起来像「这轮的账」。

### ② 一条判据的邻域取法串到了隔壁元素

`test-no-fake-actions` 判「凡是标着未实现的控件都必须真禁用」，
原本按 **±6 行**取邻域找 `disabled`。设置页里：

```
<Row label="导入" …><Button …>导入…</Button></Row>   ← 真控件
<Row label="暂不支持的导入格式" desc="…" />          ← 自闭合，纯说明
```

第二行**一个可点的东西都没有**，而它的 ±6 行里正好有上面那个 `<Button>` ——
于是一行说明文字被判成了「假按钮」。

改成问真正该问的那件事：**承载这行字的那个元素有没有子节点**（自闭合就没有）。
这个新分支配了三条自检（自闭合→不是控件 / 有子节点→是控件 / `<Button>`→是控件），
不然它可能恒真或恒假 —— **一个恒真的判据比没有判据更坏**。

### ③ 这轮回归把 Playwright 的浏览器删掉了

跑完之后 `%LOCALAPPDATA%\ms-playwright` **整个空了**，
而 `chromium.launch()` 直接报 `Executable doesn't exist`。

后果很具体：**下一次 `npm run test:all` 会有 60+ 个套件全红**，
而那些红项和代码毫无关系。已 `npx playwright install chromium` 装回（114.6MB）并复验。

**没能定位到是谁删的**：runner 的清扫只碰 `data/`，`test-container` 只删它自己那几个卷，
项目里搜不到任何碰 `ms-playwright` / `LOCALAPPDATA` 的代码。
如实记下来，免得下一个人以为是「又装一次就好了」。

> 同族提醒：**「红」要分清是「我改坏的」还是「环境坏了」**。
> 前者要修代码，后者要修环境 —— 弄反了会花很久去改本来正确的代码。

# 第 二十六节 · `npm run build` 一直是坏的，而它藏着两个真 bug（2026-10-18）

起因很小：交付镜像 `docker build` 跑不起来，我以为 Docker 有问题。
真实原因不是 Docker —— 是 `RUN npm run build` 里的 `tsc -b` **过不去**。

而 `npm run build` 坏了很久没人知道，因为**没有人真的跑过它**：
测试全走 `vite build`，那条路不经过类型检查。

## 根因：一行自我引用

```ts
// src/store/index.ts，store 字面量【内部】
togglePinDoc: (docId) => {
  const d = useStore.getState().docs[docId]   // ❌
```

store 的类型要从这个字面量推断，而这个字面量里的表达式又要先知道 store 的类型 ——
解不开，于是 **`useStore` 的类型塌掉**，
全项目每一个 `useStore((s) => …)` 拿到的 `s` 都退化成 `unknown`。

表现出来是 **380 条**错误散落在十几个文件里，
看起来像「这代码库没认真写类型」，实际上**是一个点**。
同一个文件里其他方法一直用的是 `get()`（zustand 给的取 state 入口），它不构成自我引用。

```
改成 get() 之后：380 → 0
```

## 类型检查抓出来的两个真 bug

### ① Excel / CSV 导入出来的表格，打开是坏的

```ts
sheetData: { ...(cur.sheetData || {}), sheets: [p.data], activeId: p.data.id }
```

`SheetData` 期望 `sheets` 是 **`{ sheets: SheetTab[]; activeId: string }` 这个对象**，
而代码塞进去的是**数组**。SheetView 走 `useDocSection(doc.id, 'sheets')`，
它把 `doc.sheetData.sheets` 当 `SheetData` 用（`activeTab` 会在里面 `.find()`）。

解析器那一层**完全正确**（`test-import-office` 29 项全绿），
所以**没有任何一条断言会红** —— 测的是「能不能把 xlsx 读成 SheetTab」，
没测「读出来的东西有没有被正确地存回去」。

### ② `Select` 组件**没有 `disabled` 这个属性**

`BookSettings` 的成员角色下拉传了 `disabled={!canAdmin}`，
而 `SelectProps` 里根本没这一项 → **属性被静默丢掉** → `<select>` 照样可点。

于是没有管理权的人看到一个活生生的角色下拉，点下去服务端拒绝、界面零提示。
**长得像能点、点了没反应** —— 正是这个项目一直在清的那一类。

已补上 `disabled?`，并配了看得出来的禁用态：
真禁用但外观和能点时一模一样，用户只会以为「点了没反应」。

## 顺带改对的两个类型

| 原来 | 事实 | 怎么改 |
|---|---|---|
| `Doc` 没有 `bookId` / `spaceId` | 运行时一直有（`createDoc(bookId, …)` 建出来就带着） | 声明成**可选**，并写清为什么可选 |
| `defaultBookSettings()` 推成字面量类型 | 它**故意**只有 10 个键（`blockSearch`/`blockTerms` 走表默认） | 声明返回类型 + 把「刻意的留白」写进 `BookSettings` 那两列的可选性 |

> 「五处应当一致」这个不变量**本来就不成立** —— `book_settings` 的列清单在项目里有五份、
> 各自独立维护，而这两处就该不一样。硬凑一条 lint 只会误报。

## 结论

```
类型错误   380 → 0
npm run build   之前坏 → 现在过
docker build     之前失败 → yuque-kb:test 253MB
test-container   12/1 红 → 64/0 绿
```

**教训**：
1. **`npm run build` 要当成一条真的门。** `vite build` 通过 ≠ 构建通过。
2. 类型错误**成百上千条时，先怀疑根因集中在一两个点**，别逐条加标注 ——
   按错误码聚类、按文件聚类，往往指向一处循环引用。
3. 「一个组件的属性没声明」往往是**真 bug**，不是类型洁癖：
   传了但被静默丢掉 = 那个功能其实一直没生效。
