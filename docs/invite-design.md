# 协作邀请 —— 设计与踩坑记录

**日期**：2026-10-11 · **范围**：知识库级邀请（把人拉进知识库）

---

## 一、为什么做这个

之前本项目只有「管理员单向把人加进库」（知识库设置 → 权限 → 添加成员）。
对方**没有拒绝的机会、也不知道自己被加了**。

项目里原有一套 `collaborations`，看起来像协作邀请，实际是**纯客户端种子数据**：

- 无服务端表、无 API、不在 `server/entities.ts` 的同步实体清单里
- 服务端形态下 `clearLocalSnapshot()` 把它清成 `[]`
- UI 已门控隐藏（`?tab=collab` 手敲仍能打开一个恒空的页面 + 两个假按钮）

也就是说：**那套代码是死的**。真邀请做出来之后，它还多了一个危害 ——
两套同名的「协作」并排存在，下一个人可能顺手把旧的接回去，
功能又变成「点接受、刷新就没」。

所以本轮**连带删掉它**，并加守卫钉住「假的不许复活」。

## 二、三个设计决定

### 1. 去重用**部分唯一索引**，不用整表唯一

```sql
CREATE UNIQUE INDEX idx_inv_pending
  ON book_invites(bookId, toUserId) WHERE status = 'pending';
```

整表 `(bookId, toUserId)` 唯一会让**「拒绝过之后还能再邀请」**这条正常路径
直接失败 —— 拒绝之后那一行还在表里，第二次插入就撞唯一约束。

只对 `pending` 建索引，正文拦得住重复待办，处理完的记录不占名额。

### 2. 接受时**先加成员、再改状态**

反过来（先改状态再加成员）的话，加成员失败会留下一条
「已接受但其实没进库」的记录：
用户看到邀请消失了、点进知识库却没有权限，**而两边都不报错**。

### 3. 送达只做**站内**，不做邮件

本项目没有 SMTP 配置。「已发送邀请邮件」这种话是**假的**，
而假通知比没通知更糟 —— 对方会一直等，等到以为系统坏了。

现在是对方登录后顶栏亮红点 + 工作台待办列表。
要接邮件是往 `book_invites` 上加一个投递器，**不动这张表**。

## 三、两个入口刻意**不合并**

| 入口 | 语义 | 对方有选择吗 |
|---|---|---|
| 添加成员 | 管理员**直接生效** | 没有 |
| 邀请 | 发一条待办过去 | 有（接受 / 拒绝） |

合成一个弹窗的话，用户点下去之前说不清会发生什么 ——
而这恰恰是内网场景最需要说清的一件事（把人拉进来和请人进来不是一回事）。

## 四、本轮被守卫抓到的四个真缺陷

| 守卫 | 抓到什么 | 为什么危险 |
|---|---|---|
| `test-entity-keys` | 服务端加了实体、客户端 `SHAPE` 没登记 | **静默不同步**：邀请发出去，对方刷新后待办空的，两边都不报错 |
| `test-auditgap` | 四个审计动作没有中文名 | 审计页会显示 `book.invite.send` 这种标识符，而审计页是给「出事了查是谁动的」的人看的 |
| `test-no-fake-actions` | `acceptCollaboration` / `rejectCollaboration` 成了死代码 | 留着就有人可能顺手接回去 |
| 同上 | `getSentInvites` 声明了却没人调用 | **守卫报得对**：我在权限页自己 filter 了一遍，同一口径两处各算一遍 |

最后一条补得最有价值 —— 它逼我把「库管理员也能看到别人发出去的邀请」
这条口径从界面搬进 store。理由是本项目已经吃过同族亏：
面包屑的 `crumbDoc` 在两处各算一遍，「文档标题」和「目录树标题」就分叉了，
而两边各自都测得过。

## 五、破坏对照测出来的一个**守卫漏洞**

我把 SideNav 的未读数改回读假数据（`collaborations.filter(c => c.unread)`），
**守卫全绿 321/0**。

原因：原有那条「未读数来自真实数据」只查 **TopBar**，
而 **SideNav 也在算同一个数**却没人管。

后果不只是「数字不对」：侧栏红点会**常亮**（数字来自假种子的 unread），
而点进去是空的 —— 用户看到的是一个骗人的红点。

补上那条断言后，破坏立刻被咬住（红 2 项，并把实际的错值显示在输出里）。

**「基准永远是绿的」这句话在这里的含义很具体**：
不验这一下，就会以为守卫有效。

## 六、我自己的新判据也错过三次

写这个功能时，我新加的判据错了三次，**但代码本身是对的**：

1. **没剥注释** —— 判「SMTP 有没有被引」时扫全文，
   命中的是我自己写的那句注释「本项目没有 SMTP」，
   于是一条讲「别吹牛」的断言自己判成了「在吹牛」。
   修法：只认 `import` / `require` —— 那才是真的「装了邮件客户端」。
2. **正则没容忍 `async`** —— `act: async (id) => {...}` 中间多一个 `async`，
   `\(\s*\([^)]*\)\s*=>` 匹配不上。
3. **整段替换吃掉了变量声明** —— 起点选在注释行，而上一行正是
   `const navSrc = ...`，替换后变量没了 → `ReferenceError`，
   **套件连汇总行都打不出来**（症状看起来像「没有输出」，很容易误判成超时）。
   `node --check` 查不出这个：它只管语法，不管运行时作用域。

**共同的一条**：判据红**不等于**代码错。
要先看真代码再动判据 —— 我有一次差点反过来（把对的代码改成错的来迎合判据）。

## 七、端到端覆盖

`test-invite.mjs`（31 项，自己起服务端，两个真实账号走完整条路）：

- 表结构 / 部分唯一索引 / 重复 pending 插不进去
- 发起、幂等、越权 404、待办列表带库名与邀请人名
- 接受 → **真的进 book_members**（解库查，不是只看计数）
- 同一条不能处理两次 / 拒绝 → 没进成员 / 拒绝后还能再邀请
- 撤回：邀请人本人可以，无关第三方 403
- 边界：不能邀请自己、角色不能是管理员、未登录 401、不存在的库
- 送达边界：**没有** SMTP 依赖（不许声称发过邮件）

- 文档级协作邀请（`Collaboration` 那个类型还在，与知识库级邀请是两回事）
